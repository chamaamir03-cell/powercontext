# 周边去哪儿

完成一次“理解需求 → 查询高德 → 筛选地点 → 返回推荐”。每个地点都是从用户提供的同一起点出发的独立备选。

## 1. 提取需求

- 提取城市、起点坐标、地点类型、步行时间上限、推荐数量、明确排除项和排序偏好。区分必须满足的条件与“优先、最好”等偏好。
- 坐标使用高德工具要求的 `经度,纬度` 顺序。已给坐标时直接使用，不用 IP 定位，不根据起点名称重新选择位置。坐标与城市明显冲突时请求澄清，不擅自交换或修改坐标。
- 推荐上限为 `N = min(用户指定数量, 3)`；未指定数量时为 3。用户没有给时间上限时，不自行添加硬性时间限制。
- “不超过 T 分钟、T 分钟内”按 `duration <= T × 60` 判断；“少于 T 分钟”按严格小于判断。其他明确距离、类型、区域限制也必须保留。
- 起点坐标和需求已足够时直接查询。仅在缺少必要起点或需求存在影响执行的歧义时追问。

## 2. 选择高德工具

使用平台提供的高德 MCP 工具，工具名称、参数类型、可选字段和返回结构以当前工具定义为准；不要杜撰接口或传入未支持的参数。

| 能力 | 输入与用途 |
| --- | --- |
| 周边搜索 | `location=起点坐标`、`keywords=地点类型或具体需求`；支持时设置 `radius`，取得候选 POI |
| 步行路线规划 | `origin=起点坐标`、`destination=候选 POI 坐标`，核实步行距离和耗时 |
| 地点详情（按需） | 用搜索返回的 POI ID 补齐地址、坐标、类型或与需求有关的信息 |
| 关键词搜索（按需） | 周边搜索不足或不可用时，用地点类型、城市及起点附近地名补搜；结果仍需路线验证 |

运行环境和 API Key 由平台配置；无需用户提供密钥，也不安装额外服务。若未提供必要工具，直接说明无法完成真实查询。

## 3. 搜索并整理候选

1. 将自然语言转成适合检索的类型词，例如“喝咖啡”用“咖啡馆”，“吃川菜”用“川菜”。不要把整句需求或“步行十五分钟、最多三家”等约束拼进关键词。“咖啡馆或茶馆”等多个可接受类型分别搜索并合并。
2. 以用户坐标为中心搜索。遵守用户明确的搜索半径；否则，有时间上限 T 时可从约 `100 × T` 米开始，没有时间上限时可先搜 2000 米。半径须符合工具范围；这些值只用于召回候选，不能证明步行可达。
3. 根据返回的名称、类型、地址和城市信息排除明显不符的地点。搜索结果中的距离仅用于安排核验顺序，不能写成步行距离，也不能直接决定最终排名。
4. 按 POI ID 去重；没有 ID 时结合名称、地址和坐标识别同一地点。同品牌不同门店保留区别，不合并不同分店，也不把同一地点重复推荐。
5. 保留 POI 的原始名称、地址、坐标及可用类型。缺少地址或坐标时可查详情；坐标仍缺失的地点不进入推荐。优先使用地址完整的候选；仅地址未返回、但地点身份和类型可确认且步行路线有效时，可以保留并标注“高德未返回详细地址”。不得凭常识补造街道、门牌或坐标。
6. 通常先取约 6–10 个匹配候选核验路线；不足时使用已有剩余候选，或翻页、换同义类型词、适度扩大半径补搜，仅使用工具支持的能力。补搜最多两轮，不改变用户的硬性条件。扩大搜索半径不等于放宽步行时间。

## 4. 核验步行路线

- 对准备纳入推荐的每个候选调用步行路线规划。所有调用的 `origin` 必须保持为原始起点，`destination` 必须对应当前候选 POI，不能把上一个推荐地点作为下一段起点。
- 在内部将每个 POI 与其路线一一关联，保留原始总距离、总耗时和查询是否成功。不能把某家店的路线数值套给另一家店。
- 从成功返回的完整步行方案读取总 `distance` 和 `duration`，不要误取某一段 `steps` 的数值。常规高德步行接口距离单位为米、耗时单位为秒；如当前工具明确说明其他单位，先转换。
- 若有多个完整步行方案，先排除不满足时间、距离硬性限制的方案；再按“近一点”选择距离最短的合格方案，按“快一点”或未指定偏好选择耗时最短的合格方案。距离和时间必须来自同一个方案；所有方案均不合格才按路线限制排除该地点。
- 将数值字符串解析为数值后比较。空数组、缺失字段、空字符串、非数值、负数或服务失败不视为有效路线；不能将缺失值当作 0。
- 必须按未舍入的总秒数过滤时间上限。例如 900 秒满足“不超过 15 分钟”，901 秒不满足。距离上限也按原始路线距离判断。
- 未获得有效步行总距离和总耗时的候选不进入推荐。禁止用直线距离、搜索距离、经验步速、驾车或骑行数据代替步行路线。

## 5. 过滤与排序

1. 先过滤类型、步行时间、步行距离、明确排除项等硬性条件。对价格、设施等必须满足但无法核实的条件，可按需查询详情；仍不能核实时，不将该地点列为满足全部条件的推荐，并说明限制。
2. 安静程度、排队、营业状态、评分、消费等只能依据工具实际返回的信息描述。仅有营业时间不等于已确认当前营业；无依据时标注“未核实”，不能从品牌、类型或名称推断。
3. 用户说“优先近一点、距离近”时按已核验的步行总距离升序，同距离按耗时升序；说“最快到、时间最短”时按步行总耗时升序，同耗时按距离升序。没有明确排序偏好时，先保证需求匹配，再优先步行耗时较短的地点。
4. 排序覆盖本轮已核验的有效候选，不直接沿用搜索返回顺序。不因最先查到的 N 家合格就跳过已选待核验候选；搜索距离较短的候选可能实际绕行更远。
5. 返回排序后的前 N 个。可以少于 N 个或为零，不能用超时、类型不符、路线失败或重复地点凑数。仅对已查询核验的候选作比较，不宣称找到全城或全范围的绝对最近地点。

## 6. 生成简洁回答

先用一句话交代起点、主要限制和排序方式，然后用列表或表格给出结果：

| 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |

- 每行使用高德实际返回的地点名称和地址（缺失时按第 3 节标注），保留分店名；理由用一句话说明已证实的类型匹配、路线距离、耗时或排序优势。
- 距离优先展示原始米数。时间展示为分钟与秒，整分钟可省略秒；明确这是高德路线预计值。例如返回 845 秒时写“约 14 分 5 秒”，不改写成恰好 14 分钟。
- 不向用户展示内部推理、候选台账或工具调用日志。无需额外导出 JSON、上传日志或生成多站行程。
- 有未核实偏好时在对应理由或表后说明，如“安静程度、排队及当前营业状态未核实”；只提示与本次需求有关的不确定信息。
- 不足数量时说明“本次查询仅核实到 X 个符合条件的地点”，并按真实情况解释其余候选超时、类型不符或路线未能核实；不要笼统宣称附近没有其他地点。
- 零结果时不填造推荐行。搜索与路线核验均正常、但没有合格地点时，说明“本次查询范围内未找到符合条件的地点”，可建议放宽时间、范围或类型，不自行放宽。若有路线查询失败，说明“本次未能核实到符合条件的地点”并指出失败情况，不能把未核实当成不符合；所有路线失败时按第 7 节说明。

## 7. 查询异常

- 超时、限流或临时服务错误，对同一次请求最多重试一次；参数错误仅在能依据工具定义修正时重试。认证或权限错误不反复调用。
- 地点搜索成功但某个路线失败时，继续核验其他候选；必要时补搜。保留已成功核验的结果，说明存在未能核实的路线，不声称失败地点不可步行到达。
- 不能完成搜索或所有路线均无法核实时，明确说明“高德地点查询失败”或“步行路线暂未能核实”，不给出虚构地点和距离时间。服务失败与查询成功但没有合格结果要区分。

输出前确认：每行都有对应的高德 POI 和从同一起点到该 POI 的有效步行路线；原始数值满足硬性条件；数量、排序、单位和推荐理由一致；缺少依据的信息已如实说明。
